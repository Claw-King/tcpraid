# 安全

这份文档讲 tcpraid 保护什么、不保护什么，以及每一样机密值多少。这里讲的是节点(`tcpraid run`)，手动模式在 `manual-mode.md` 里有自己的一节。

## 一段话概括

两个配对过的节点靠密钥认识对方。默认情况下它们之间的每条连接都是 TLS 1.3，并对照配对时记下的指纹做双向认证。节点承载的内容，在应用和它的节点之间、以及远端节点和目的地之间，又回到明文。配对过的节点被完全信任，除非你加以限制。网页界面和本机 API 是明文 HTTP，由密码和令牌把守。

## 线路上是什么

| 路段 | 保护 |
|---|---|
| 应用到它的节点 | tcpraid 不提供：取决于应用自己怎么做 |
| 节点到节点，`tls` 档(默认) | TLS 1.3；两端各自把对方的密钥和配对时记下的指纹进行核对 |
| 节点到节点，`owncert` 档 | TLS 1.3；监听的节点出示你提供的证书，由拨出的节点按证书密钥的指纹、或者按签发机构和主机名核对；拨出的节点出示它的身份证书 |
| 节点到节点，`off` 档 | 没有：明文 TCP。只有经过认证的开场白和经过认证的传输层消息 |
| 远端节点到目的地 | tcpraid 不提供 |

只有当别的东西已经把一条路径从节点到节点全程加密时，才在这条路径上用 `off`，比如 VPN 或者加密的代理链。在这一档里，开场白是证明拨出者身份的唯一依据，而有人在路径上录下的开场白可以在十分钟内被再次发送。

无论哪一档，两个节点之间的连接都以一段简短的开场白开头。开场白里有拨出节点的指纹、时间和一个随机数，再用配对密钥派生出的密钥做 MAC(HMAC-SHA256)。监听节点遇到核对不过的开场白，或者其中的时间和自己的时钟相差超过十分钟，就直接关闭连接，不作任何回答。之后传输层用配对密钥派生出的另一把密钥认证自己的报文头和回执。任何两对节点都不会共用这些密钥。

用到的一切都来自 Go 的标准库：TLS 1.3、X.509、Ed25519、HMAC-SHA256，UDP 回执用 AES-256-GCM。没有 tcpraid 自己设计的密码算法。

## 配对

配对码里有要连接的地址、生成它的节点的指纹和一个一次性密钥。加入的节点用 TLS 1.3 连过去，只有当它连到的节点确实是这个指纹时才继续。然后它证明自己持有那个密钥，这个证明和这一条连接绑定。两个节点各自从这条连接派生出**配对密钥**(32 字节)，它从不在网络上传输。

- 一个配对码只能用于一次配对，有效期一小时。`-ttl` 可以改这个时间，最长 30 天。用过、过期或作废的配对码不能再用。
- **配对码在用掉之前要当作机密对待。** 谁先拿到它，谁就能顶替你去配对。你会发现的，因为你自己的尝试被拒绝，而生成配对码的节点上列出了一个你不认识的对端。遇到这种情况，把那个配对解除掉。
- 只凭配对码，没有人能冒充生成它的节点。
- 对同一个配对码给出五次错误的证明之后，这个配对码被作废。
- 请通过网页界面输入配对码，或者从 `tcpraid pair join` 的标准输入输入。作为命令行参数给出的话，它会出现在进程列表里，并留在 shell 的历史里。

生成配对码的节点保存的是配对码的编号和那个密钥的哈希，而不是配对码本身。证明就是用这个哈希做的，所以在配对码有效期内，它和配对码一样管用。能读到这个节点上 `state.json` 的人，可以顶替这个配对码本来要给的节点去配对。

配对可能被中途打断，因为它发生在两台机器上，没法在同一瞬间在两边同时完成。如果生成配对码的节点接受了，而它的回答在路上丢了，这个节点会列出新的对端，并在日志里写明，加入的节点则报告失败。这时用一个新的配对码把它们重新配对。

## 对端能做什么

和一个节点配对，就是信任它。经过规则，对端的连接从你的节点出来，可以去往**你的节点能连到的任何地址**，无论在你的局域网里还是外面。

要收窄这个范围，就在对端的连接出来的节点上，给这个对端设一个允许列表。列表里是若干网段，可带端口或端口段，用逗号分隔。在网页界面里，它在 对端 > 详情 > 高级 >“对端可以访问的目的地”。用命令：

```
tcpraid peers set nas-b -allow 192.0.2.10/32:873,192.0.2.10/32:50000-50010
```

`-allow ""` 把列表去掉。API 里有同一项设置 `PUT /api/v1/peers/NAME`，见 `reference-api.md`。

去往其他任何地方的连接都会被拒绝，另一端的应用会看到连接被重置。对端会被告知原因是允许列表，并把它显示在自己那条规则的状态里。你的节点连不上某个目的地时，对端被告知的是系统给出的错误，里面只有它自己要连的那个目的地。

允许列表不管路径测试(`tcpraid peers test`)，因为测试数据在你的节点里就结束了，不去往任何地址。对端随时可以让你的节点接收这样的数据。你的节点自己给它设了上限，不指望对端守规矩：同一时间最多四个测试会话，每个到 90 秒或 1 GiB 就结束。

解除配对(`tcpraid peers remove NAME`，或者“解除配对”)会重置和这个对端之间两个方向上的会话，并从此拒绝它的连接。另一个节点不会收到通知，仍然会列出这个节点。指向被移除对端的规则会保留。以后用同一个名字配对的节点会接手它们，如果不希望这样，就把它们删掉或改掉。

## 数据目录

| 文件 | 值多少 |
|---|---|
| `identity.key` | 节点的私钥。有了它，别人可以在它的对端面前冒充这个节点 |
| `state.json` | 里面有各个配对密钥，在配对码有效期间还有其密钥的哈希。有了配对密钥，别人就能通过那个配对的开场白；在 `off` 档下，这就是全部所需 |
| `api.token` | 通过本机 API 完全控制这个节点 |
| `ui.password` | 网页界面密码的加盐哈希(PBKDF2-HMAC-SHA256)，绝不是密码本身 |

目录以 0700 的权限创建，含有机密的文件是 0600。证书是公开的，权限是 0644。启动时如果同组用户或其他用户能写这个目录，或者能读密钥或令牌，节点会给出警告。在 Windows 上这些权限位不说明谁能访问，访问由文件夹的权限决定，节点也不发这种警告。**像备份私钥那样备份这个目录，不要让两个节点共用。**

## 网页界面和本机 API

- **明文 HTTP。** 密码、令牌和其他所有内容，在浏览器或程序与节点之间不加密地经过网络。API 默认监听 `127.0.0.1`。把它开放给其他主机时(`-api 0.0.0.0:9850`，容器里就是这样)，请在你信任的网络上这样做，或者在前面放一个带 TLS 的反向代理。节点会在日志里提醒这一点。
- 登录了的人，或者持有令牌的人，什么都能做，包括给节点配对，以及经由规则访问对端能访问的一切。请像对待令牌那样对待密码。
- 一次登录持续 12 小时，或者直到点击“退出登录”为止。cookie 不能被脚本读取，也不会随其他站点发起的请求一起发送。会修改东西的请求还必须带上请求头 `X-Tcpraid-Request: 1`，其他站点的页面没法让浏览器发出这个请求头。
- 浏览器按主机名而不是按端口保存 cookie，所以同一个主机名下的其他网页服务也会收到这个 cookie，同一台主机上的两个节点会互相把对方登出。
- 同一个地址连续输错 5 次密码之后，登录对这个地址关闭一分钟。在反向代理后面，所有访客共用这个计数。
- 密码从不保存。自动生成的密码只在第一次启动的日志里显示一次。

## 监听和未认证的连接

任何能连到节点监听的人都可以向它发起连接，所以每个监听只保留有限数量的、尚未证明自己身份的连接。上限是 2048 条，或者进程可打开文件数的四分之一，取较小者。新来的连接总是被接收。监听满了的时候，等得最久的一条被关掉腾出位置。如果某个来源地址占用了超过八分之一的名额，就改为关掉占得最多的来源里最老的一条。什么都不发的连接 3 秒后被关闭，握手的时限是 15 秒。

这限制了“占着连接不放”能造成的影响，但并不让监听免疫。如果有人在一次握手所需的时间内，送来差不多和监听名额一样多的新连接，只要他一直这样做，就能把对端的握手挤掉。这个数量估计是每秒几千条，没有实测过。已经建立的连接绝不会因此被关闭。接受连接出错时，例如文件描述符用完了，节点会继续监听。

## tcpraid 不做的事

- 它不加密应用和它的节点之间、以及远端节点和目的地之间的部分。
- 数据目录、令牌或密码落到别人手里的节点，它保护不了。
- 它没有经过独立的安全审计。
