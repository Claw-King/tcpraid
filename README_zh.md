# tcpraid

tcpraid 把**一条 TCP 连接**拆到**多条 TCP 连接**上传输，在对端按原来的顺序重新拼好。应用程序不用改，也察觉不到。

有些软件做大量传输时只开一条 TCP 连接，比如存储复制、备份流、数据库复制。tcpraid 就是给它们用的，适合线路长或者有丢包的情况，这时单条连接又慢又不稳，多条并行却跑得很好。

名字借用了 RAID 的想法，也就是几个普通的成员合在一起，比单独一个更快、更可靠。

状态：0.1，第一个公开版本。线路协议是版本 1(见 `PROTOCOL.md`)，在 1.0 之前仍可能变动。依赖它之前，请先读下面的“已知限制”。

## 它适合你吗？

下面几条都成立时，它有帮助：

- 你有一条长时间的大流量数据流，它自己没法拆成多条并行连接。这里有教程的例子：TrueNAS 上的 ZFS 复制、rsync 守护进程、PostgreSQL 流复制、Proxmox Backup Server 的同步任务。
- 在你的线路上，多条并行的 TCP 连接合起来明显比一条更快或更稳。想快速试一下，可以用网络测速工具 `iperf3` 分别跑一条流和八条流。两个节点配对之后，`tcpraid peers test` 可以在节点自己的路径上测同一件事。
- 两端你都能运行 tcpraid。

除了速度，它还带来：

- **断线不会让数据流中断。** 所有子连接都断了的时候，两端会把应用的连接保持最长 15 分钟，线路恢复后接着传。
- **被截断的数据流不会被当成完整的。** 异常结束时，两边应用的连接都会被重置。节点被正常停止时如此，节点的进程被强行杀掉或者内存耗尽时也如此，因为节点一拿到应用的连接就做好了设置，进程一旦消失，系统就会重置这条连接。还剩两种情况，列在“已知限制”里：节点停止时的一条空连接，以及整台机器断电。0.11.0 之前的版本还有第三种，也列在那里。
- **两个节点之间默认加密**(TLS 1.3)。每个节点都会把对方的密钥和配对时记下的进行核对。

这些情况下它帮不上忙：

- 一条 TCP 连接已经能跑满线路。
- 线路又短又干净，比如局域网或邻近的数据中心。
- 线路本身很好，而单独那条连接的套接字缓冲区又足够大。这时一条连接可能和多条一样快，甚至更快。tcpraid 的好处主要体现在有丢包的线路上，在那里它更稳，而且不需要任何人去调大缓冲区。
- 两个节点之间有东西把它们的连接并进了一条连接里，比如 SSH 端口转发，或者默认设置的 frp。这时 tcpraid 照样能用，但不会带来任何好处。哪些工具会这样、该怎么设，见 `docs/zh/connecting.md`。
- 应用自己就能开并行连接。这时直接用应用自己的功能。
- 应用要一点数据，等它到了才要下一点。这时它的速度是一次要多少除以往返的时间，tcpraid 能做的很少。打开另一个站点的文件共享可能就是这样，`docs/zh/tutorial-file-share.md` 讲了怎样改善。

它不是 VPN，也不是通用代理。它只承载你为之建了规则的那些 TCP 连接，而且只在你自己运行的两台机器之间。

## 怎么用

在每个站点运行一个**节点**，可以装在 NAS 本机上、容器里，也可以装在为局域网服务的路由器或网关上。把两个节点**配对**一次，做法是在一个节点上生成配对码，复制到另一个节点上。之后在任意一个节点上建**转发规则**，意思是“到达这个端口的连接，送到另一个站点的那个地址”。

```
 application --> [ node B ] ===== several TCP connections =====> [ node A ] --> destination
                  rule: port 9801 -> 192.0.2.10:873 at node A's site
```

两个节点里只要有一个能被另一个连到就行。所有操作都可以在节点的网页界面里完成，也可以用 `tcpraid` 命令完成。

目的地固定的规则是应用最常用的入口。另外还有三种。透明规则接路由器重定向到节点的连接。SOCKS5 规则接会说 SOCKS5 的程序，每个程序自己说出要去的目的地。`tcpraid connect` 把单独一条连接接在一条命令的标准输入和标准输出上，供 `ssh` 这类靠运行命令来连服务器的程序使用。这几种都在 `docs/zh/reference-cli.md` 里说明。

给运维的人另外还有四样东西。`tcpraid config export` 把节点的配置写成一份不含秘密的文件，`tcpraid config apply` 让节点变成这样一份文件描述的样子。`-metrics` 把节点的各项数字提供给监控系统。`-hook` 在对端上线下线、会话开始结束时运行你的一个程序。Go 程序可以通过 `client` 包使用节点。

出了问题，节点会告诉你该看哪里。`tcpraid rules` 显示规则最近一条连接为什么失败，连同另一个节点给出的原因。`tcpraid sessions` 显示一次传输是在走，还是在等线路，以及还会等多久。`tcpraid peers test` 测出在你的线路上，多条连接比一条多带了多少。路径测试只有命令和 API，网页界面里没有。

## 五分钟上手

例子里有两台机器：`nas-a`(另一台可以通过 `nas-a.example.org` 连到它)和 `nas-b`。两台都用容器运行节点，用的是 `deploy/docker-compose.yml`：

1. **在每台机器上启动一个节点。** 执行 `docker compose up -d`，再执行 `docker logs tcpraid`。日志里会显示网页界面的密码，只显示这一次。
2. **打开每个节点的网页界面**，地址是 `http://NAS-的地址:9850/`。
3. **给它们起名字，再配对。** 新节点的名字是主机名加上四个随机字符，例如 `tcpraid-k3x9`。在 设置 >“本节点的名字”里给每个节点起一个认得出的名字，这里用 `nas-a` 和 `nas-b`。要在配对之前做，因为节点记住的是对端在配对那一刻的名字。在 `nas-a` 上进入 对端 >“生成配对码”，在“对方用什么地址连到本节点”里填 `nas-a.example.org:9851`，点“生成”，然后复制配对码。在 `nas-b` 上进入 对端 >“输入配对码”，粘贴进去。现在两边的页面都显示对方在线。
4. **建一条规则。** 在 `nas-b` 上进入 规则 >“新建规则”。监听地址和端口填 `0.0.0.0:50000`，对端选 `nas-a`，目的地填 `192.0.2.10:873`，这是从 `nas-a` 看过去的地址。
5. **用起来。** 让应用连 `nas-b` 的 50000 端口，而不是 `192.0.2.10` 的 873 端口。

同样的事可以用命令来做，这里是在容器里执行的。不用容器时去掉 `docker exec ... /` 和 `-data /data`：

```
nas-a$ docker exec tcpraid /tcpraid pair create -data /data -addr nas-a.example.org:9851
tcpraid-pair-1-iiph6pbe4iey...
nas-b$ docker exec -i tcpraid /tcpraid pair join -data /data
tcpraid-pair-1-iiph6pbe4iey...        <- pasted; then Enter and Ctrl-D
paired with nas-a (fingerprint 056f8829...e2e077d8)
nas-b$ docker exec tcpraid /tcpraid rules add rsync -data /data -peer nas-a \
           -listen 0.0.0.0:50000 -dest 192.0.2.10:873
rule rsync added: listening
```

`docs/zh/install-container.md` 和 `docs/zh/install-binary.md` 会把这个过程慢慢讲一遍。

## 要求

- **每一端是 Linux、macOS 或 Windows。** 两端不必是同一种系统。在 Linux(amd64、arm64 或 32 位 ARM v7)上用容器或者一个静态二进制文件。在 macOS 和 Windows 上用一个二进制文件，没有“已知限制”里列出的那几项功能。
- **每一端都要有一个节点。** 远端只有一台普通的服务器是不够的。
- **两个节点里有一个能向另一个发起 TCP 连接**，直接连，或者经过端口转发、隧道或 SOCKS5 代理。做到这一点，两个站点都不需要有公网 IPv4 地址，几种办法在 `docs/zh/connecting.md` 里逐一讲了。
- **只承载应用的 TCP 流量。**
- **内存。** 最坏情况下一个节点会缓存约 512 MB 的流数据。这个数是 `-budget` 的两倍，`tcpraid run` 可以把它调小。
- **两端的时钟相差不超过 10 分钟。**

## 已知限制

这是第一个版本，由一个开发者用业余时间做成。已经知道的：

- **macOS 和 Windows 是新加的，功能也少一些。** 这个程序是在 Linux 上写出来、用起来的。在 macOS 和 Windows 上，到目前为止它经过了仓库的自动测试和一次手动试用。那一次是同一个局域网里的一台 Mac(Apple 芯片)和一台 Windows 机器(amd64)在网页界面里配对，1 GiB 的数据从一台传到另一台，两端校验值一致。只在 Linux 上有的功能：透明规则(`-transparent`、`-redirect`)、`-maxrss`、路径上的套接字标记、容器镜像、systemd 单元。
- **只在很少的机器上测过。** 教程是在容器里跑的，用普通程序代替 NAS。0.1.0 版发布之后，它的第一位用户在真实的机器上跑过它，包括 amd64 和 arm64 的主机，以及两个站点的路由器上的容器(见“实际使用的结果”)。还有两件事没有试过。教程里要在 NAS 的网页界面里做的那些步骤，没有在任何品牌的真实 NAS 上做过。Unraid 和 QNAP 的容器模板只对照公开的格式核对过。
- **传输层的设置只在默认值下用过。** 从 0.7.0 版起，节点接受更多这样的设置，可以给节点设，也可以只给一个对端或一条规则设。默认值以外的取值只经过了仓库里的测试，没有在真实线路上跑过传输。文档写了每一项设置改的是什么，不给出该用什么值。
- **网页界面用得很少。** 它由脚本渲染并点击过一遍，另有一个人用它给两个节点配过对。0.8.0 版新增的部分，也就是传输设置那一块和配对码表单里预先填好的地址，是由脚本在没有浏览器的情况下跑过的，还没有人在浏览器里看过。经 TLS 提供的页面(`-api-tls`)也一样：对它跑过各条命令和 `curl`，没有用过浏览器。
- **规则的目的地写主机名时，两个节点都要是 0.4.0 或更新的版本。** 名字由对端解析，每条连接解析一次。两条连接之间不保留结果，所以每条连接都要先等这一次解析。
- **被别的调用拿走的重置，0.11.0 之前的版本有。** 一条连接上到达的重置，系统只报告给一次调用。如果拿到它的是节点的一次写入，节点对同一条连接的读取看到的就是普通的结束。0.10.1 之前的版本可能把这样的重置当成一条完整数据流的结束传过去，在一个专门为触发它而写的测试里，每一百条这样的连接有几条这样结束。从 0.10.1 版起，节点在往应用写数据的地方、在应答 SOCKS5 客户端和 `connect` 请求的地方都考虑到了这一点。从 0.11.0 版起，开着 `-api-tls` 时节点在通往 API 的连接上结束自己那一侧的地方也考虑到了，那也是一次写入。
- **停止节点时，恰好有目的地还在连接中。** 如果在停止一个节点的那一刻，有一个刚开始的会话正在这个节点上连它的目的地，目的地可能看到一条刚打开就又关上、没有任何数据的连接，像一条空的数据流。
- **会话撑不过任何一个节点的重启。** 应用会看到连接被重置，需要重试。被停止或被杀掉的节点旁边的应用，立刻就能看到。另一个节点旁边的应用，在前一个节点是被正常停止的情况下也立刻就能看到，因为停止的节点会通知对端。如果前一个节点是被杀掉的，要等它回来、两个节点重新连上之后才看到，通常在几秒之内。回来的节点会说明自己是一个新的进程，另一个节点随即重置它还为旧进程保留着的会话。节点一直不回来时，另一个节点要等到那 15 分钟(`-grace`)耗尽。会话开始后只过了几秒(最多十秒左右)对端就被杀掉时也要等这么久，除非两个节点都是 0.11.0 或更新的版本：这样的节点会问新的进程它持有其中哪些会话，并重置其余的。0.1.1 及更早版本的节点既不会说明自己是新的进程，也不理会对端的这个说明。两个节点里只要有一个是这样的版本，一个节点被杀掉后，另一个就可能要等满 15 分钟。
- **整台机器断电或死机**时什么都发不出来。它旁边的应用要等到自己的超时才知道连接已经结束。另一个站点的节点按上一条所说的方式保留会话。
- **两个节点里必须有一个能被另一个连到。** 不经第三台机器中转。一条路径可以写多个地址，按顺序尝试。节点通往对端的路径不通时，只有在对端也持有通往它的路径的情况下，才会改请对端来打开连接。这个切换要几秒到一分钟左右，正在跑的会话不会被挪过去。带 `-dial both` 的规则，一个会话里同时有两个节点打开的子连接，一个节点的路径断了，会话靠另一个节点的子连接继续(见 `docs/zh/connecting.md`)。
- **systemd 单元只用 `systemd-analyze` 检查过。** 它让节点以一个专用的用户运行，并加了一组限制。它没有在任何机器上安装或启动过。
- **网页界面和本机 API 是明文 HTTP，除非节点带 `-api-tls` 启动。** 不带时，请在你信任的网络里使用，或者放在带 TLS 的反向代理后面。带上之后，节点用它自己生成的一张证书提供这两者，浏览器不认识这张证书，会先问你(见 `docs/zh/security.md`)。
- **有人占着大量连接不放时，监听端口能限制它造成的影响，但不能完全杜绝**(见 `docs/zh/security.md`)。
- **线路协议只有一个版本。** 两个节点互相说明各自会说哪些版本、在第一个发布版本之外还会做什么，只用双方都列出的(见 `PROTOCOL.md`)。对端列出的版本里没有本节点会说的时，节点和它之间什么都不承载，`tcpraid peers` 会写明。到现在为止每个发布版本说的都是版本 1，所以这种情况只在测试里跑过。
- **有三样东西要两个节点都是 0.11.0 版。** 第一样是 SOCKS5 规则和 `tcpraid connect` 等另一个节点连上目的地才回答“连上了”。第二样是目的地拒绝连接时 SOCKS5 的专用应答码。第三样是重置对端被杀前几秒才开始的会话。另一端是更旧的节点时，节点在另一个节点接下连接 150 毫秒之后就告诉客户端连接开始了，完全没有回应的目的地看起来是一条已经开始、随后被重置的连接。`tcpraid connect` 用退出状态说明全部输入有没有传过去，这一样只要求和命令在同一台主机上的节点是 0.11.0 版。
- **“连上了”这句话可能丢。** 另一个节点连上目的地之后，在控制连接上只说一次。控制连接如果正好在那一刻断开，这句话就到不了。协议要等到应答才开始发数据的客户端，会在 12 秒之后被告知连接没有开始，而目的地其实已经连上了。先开口的是目的地时不受影响。
- **`tcpraid connect` 的退出状态 0 说的是输入到了哪里，不是它被读了。** 它表示另一个节点把全部输入写进了它通往目的地的连接，并按顺序结束了那个方向。目的地的程序有没有读，节点看不到。另一端是更旧的节点时，状态 0 说的可能还要少一些。0.11.0 版的节点被强行杀掉，或者 0.11.0 和 0.11.1 版的节点被停止，而这发生在它写完最后一点输入之后大约一秒内，这时它通往目的地的连接会被重置，目的地还没取走的数据就丢了。从 0.11.2 版起，这两种情况下剩下的数据都由系统送完。这要求节点所在主机的网络在节点退出之后还在。节点是容器的主进程、容器的网络又随它一起撤掉时(例如对用自己网络的容器执行 `docker stop`)，剩下的数据仍然可能丢，目的地这时既看不到结束也看不到重置。在这一秒里被停止的节点还会告诉另一个节点会话被中止了，所以目的地其实全部收到时，命令也可能以状态 4 结束。命令比两个方向结束大约晚一秒才结束，因为它要等节点的回答。SOCKS5 规则和 `tcpraid connect` 在容器里跑过，SOCKS5 客户端用的是 `curl`。
- **导出的配置不是备份。** 里面没有密钥，也没有配对密钥，所以它不能把节点找回来，也不能替节点配对。那要靠保留数据目录。
- **钩子看不到每一个事件。** 节点同时最多运行四个，并且不等它们。事件来得比钩子返回得快时，多出来的被漏掉并计数。
- **Go 包 `client` 在 1.0 版之前还可能改动。**
- **节点自己安装的重定向规则(`-redirect`)**是在容器里用 nftables 1.0.9 跑的，跑的是 IPv4。容器镜像里没有 `nft`，所以镜像装不了这些规则。被强行杀掉的节点会把它的表留下，直到它再次运行。
- **经 SOCKS5 的路径、`owncert` 档**在程序的测试里是通的，但教程的实际运行和在真实机器上的第一次使用都没有涉及它们。

## 实际使用的结果

下面来自作者自己的使用，用的是这个程序的前身，手动模式，一条约 240 毫秒的洲际线路，负载是存储复制：

- 一条 205 GB 的数据流平均 85 MB/s，约 4% 的数据块被重发过。
- 一条 7 TiB 的数据流跑了五天。其间它的数据通路中断过一次，持续 10 分钟，会话保持住了，之后接着传。

这些是在一条线路上的单次测量，不是基准测试，而且不是用这个版本测的。

之后，0.1.0 版由它的第一位用户以节点的方式跑过：

- 一台 amd64 主机和一台 arm64 主机之间：8 GiB 随机数据，两端校验值相同。
- 两个站点的路由器上的容器之间，经一条长距离线路，`tls` 档，一条路径传数据、一条路径负责补发和回执，同时有经 UDP 的回执，连接由规则所在节点的对端发起：20 GiB 随机数据，两端校验值相同，重发的不到 1%。
- 在这两台路由器上，一个现有的存储复制任务被重定向(`prerouting`)给节点，由一条透明规则承载，跑到了结束，存储系统上什么都没有改。

这些同样是单次运行。
